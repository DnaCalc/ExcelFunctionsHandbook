# MOD

## What it does

`MOD(number, divisor)` returns the floored remainder. For ordinary nonzero remainders the result follows the divisor’s sign. Noninteger inputs are allowed. The mathematical identity is `number-divisor*INT(number/divisor)`.

## Try it

`=MOD(-7,3)` returns `2`: `-7 = (-3)*3+2`. `=MOD(7,-3)` returns `-2`. With binary64 decimal inputs, the recorded `MOD(10,0.1)` is `0.09999999999999945`, not zero.

## Quirks

A zero divisor gives `#DIV/0!`. Recorded Excel returns `#NUM!` when the rounded quotient magnitude reaches `1.1259e12`, although a mathematical remainder still exists. Tiny operands can return the wrong sign-adjusted magnitude or `#NUM!`; these are compatibility rules, not properties of mathematical modulo. The prior explanation that Excel necessarily subtracts two large approximate products is not supported by the later exact-remainder evidence.

## How to implement

Use `R(op)` as defined in the [stored arithmetic recipe](FUNC.VAR.S.md#how-to-implement).

1. Coerce both arguments, reject a zero divisor, and return zero for a zero dividend. Compute `q=R(number/divisor)`; reject `abs(q)>=1.1259e12` or a nonfinite quotient.
2. Compute the **truncating** binary64 remainder `r`, using a correctly implemented `fmod` primitive or integer significand/exponent reduction. Do not compute `number-divisor*floor(q)` in floating point: that can lose the small remainder.
3. If `r` is nonzero and has the divisor’s opposite sign, normally set `v=R(r+divisor)`. If that addition rounds exactly to the divisor, the current compatibility rule returns zero.
4. Before that addition, a **subnormal** `r` of the opposite sign needs a special branch. With `a=abs(divisor)` and ordinary binary64 operations, set `c=(2^27+1)*a`, `low=a-(c-(c-a))`. A subnormal `low`, or `abs(q)>=2^26`, gives `#NUM!`. Otherwise, if `abs(r)<2^-1026`, return `R(a+abs(r))` with the divisor’s sign. A larger remainder takes the normal addition.
5. If no sign adjustment is needed, keep `r`. Any subnormal final result is `#NUM!`.

Worked ordinary path: `fmod(-7,3)=-1`; the signs differ, so `-1+3=2`. Worked large-quotient refusal: `MOD(1125899999999,1)` is recorded as zero, while `MOD(1125900000000,1)` is `#NUM!`.

Worked tiny path: inputs `-1.223247290044572e-296` and `1.223247290044539e-296` have an opposite-sign subnormal remainder. The recorded special branch adds its magnitude and returns `1.223247290044572e-296`, larger than the divisor. The mathematically correct remainder is `1.2232472900445062e-296`. The note retains input and result bits.

The rule matches the cited recorded bank and fresh probes. Interpreting the split as evidence of a Dekker product is an inference; the measured rule does not reveal Microsoft’s private implementation.

## Alternatives

[QUOTIENT](FUNC.QUOTIENT.md) truncates the quotient, so pairing it with MOD does not reconstruct mixed-sign inputs. [INT](FUNC.INT.md) supplies the floor convention; a language’s `%` may use another convention.

### FN-MOD-001: MOD with tiny operands gives wrong signs and #NUM!, by a rule that fits every recorded row

*Excel differs from the mathematical answer; measured; recorded 2026-11-04.*

MOD(n,d) takes the exact remainder r of n by d and adds d when their signs differ. Three things
change when r is subnormal and its sign differs from d's. The result is #NUM! when |n/d| is
2^26 or more, or when d's low part under a Veltkamp split at 2^27 + 1 is subnormal. Otherwise,
when |r| is below 2^-1026, the result is |d| + |r| with d's sign: the remainder is added where
it should be taken away. A larger r takes the ordinary step. Any subnormal final result is
#NUM!. So MOD(-(1+121*2^-52)*2^-983, 2^-983) returns +(1+121*2^-52)*2^-983, and MOD(2^-983,
-(1+120*2^-52)*2^-983) returns #NUM!, where the exact answers are ordinary numbers.

| Call | Inputs (binary64) | Excel | Correct value | Recorded in |
|---|---|---|---|---|
| `MOD(-1.223247290044572e-296, 1.223247290044539e-296)` | number `-1.223247290044572e-296` (`0x8280000000000079`); divisor `1.223247290044539e-296` (`0x0280000000000000`) (cells) | `1.223247290044572e-296` (`0x0280000000000079`) | `1.2232472900445062e-296` (`0x027fffffffffff0e`) | Excel 16.0 build 20430, Windows 64-bit, CPU not recorded in this capture |
| `MOD(1.223247290044539e-296, -1.2232472900445716e-296)` | number `1.223247290044539e-296` (`0x0280000000000000`); divisor `-1.2232472900445716e-296` (`0x8280000000000078`) (cells) | `#NUM!` | `-3.25938553492266e-310` (`0x80003c0000000000`) | Excel 16.0 build 20430, Windows 64-bit, CPU not recorded in this capture |

Correct value: MOD(n,d) = n - d*INT(n/d) in exact rational arithmetic; the result is exactly
representable.

Basis (measured): All 152,432 recorded MOD rows match, 4,974 of them rows the ordinary step
misses, and so do 1,128 new Excel readings (build 20527). Those readings overturned an earlier
test on power-of-two divisors: 1E-296 behaves like a power of two and 1E-300 does not.

Inferred, not measured: The rule is what is measured. Reading it as Veltkamp's split, the parts
of a Dekker product of the count and the divisor, is an interpretation: a table over exponent
and trailing zeros puts the boundary between exponents -1000 and -990 and at about 27 trailing
zeros.
