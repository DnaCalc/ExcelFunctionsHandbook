# BITXOR

## What it does

`BITXOR(number1, number2)` combines two nonnegative integers bit by bit. A result bit is one when exactly one input bits are one. The returned value is a decimal worksheet number.

## Try it

`=BITXOR(12,10)` returns `6`. In four bits the inputs are `1100` and `1010`; applying XOR gives `0110`.

## Quirks

Both inputs must already be integers in `0..2^48-1` (`281474976710655`). Fractions are rejected with `#NUM!`, rather than truncated. Nonnumeric arguments give `#VALUE!`. Negative numbers do not denote a signed two’s-complement operand in this family.

## How to implement

Coerce and validate the two numbers before integer conversion. Use a type able to retain all 48 admitted bits, then compute `left ^ right` and convert the result to binary64. Every admitted integer and result is exactly representable in binary64. Languages whose bitwise operators first narrow to 32 bits need a wider integer or arbitrary-precision integer path. The four-bit example uses no approximation; validation and error ordering are the separate worksheet obligations.

## Alternatives

[BITAND](FUNC.BITAND.md) retains shared bits and [BITOR](FUNC.BITOR.md) retains either operand’s set bits. [BITLSHIFT](FUNC.BITLSHIFT.md) moves a pattern without combining two operands.

### FN-BITAND-001: Bitwise functions reject fractional operands with #NUM! instead of truncating them, while shift counts truncate

*Quirk; measured; recorded 2026-11-22.* Applies to BITAND, BITLSHIFT, BITOR, BITRSHIFT, BITXOR.

In Excel 16.0 build 20430, the bitwise operand arguments (number, number1, number2) must
already be integers in [0, 2^48 - 1]; any fractional part (such as 0.1 or 1.5) returns #NUM!
rather than truncating toward zero. By contrast, shift_amount in BITLSHIFT and BITRSHIFT
truncates toward zero (e.g. -13.5 becomes -13). All five bitwise functions match 100% of their
full-bank rows (5,989 each for BITAND/BITOR/BITXOR; 8,131 for BITLSHIFT; 8,128 for BITRSHIFT).
