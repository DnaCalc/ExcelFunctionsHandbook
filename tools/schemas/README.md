# `tools/schemas/` — the schema set

Twenty JSON Schema 2020-12 files, one per file family that `FOUNDATION.md` §2 specifies. They are
the contract every other tool in `tools/` is checked against, and they are checked by
`tools/efh-validate`.

```
cd tools/efh-validate
cargo build --release
./target/release/efh-validate selftest        # the three T1 acceptance tests
./target/release/efh-validate check-organ     # validate every JSON file under data/ and content/
./target/release/efh-validate schemas         # this table, generated
./target/release/efh-validate field-reads     # the enumerated §3.7 field reads
```

`efh-validate` is a standalone crate. It is **not** a workspace member and has **no** dependency on
`oxfunc_core` — `FOUNDATION.md` §6 line 1181 puts T1 at the root of the tool graph with
`Depends on: —`, and the tool that checks the others must not need a built OxFunc to run. Its only
dependency is `serde_json` (14 crates in the lock file); a `cargo clean` followed by
`cargo build --release` measured **12.7 s** on the development host, and an incremental rebuild
measured **2.6 s**.

### The discriminator this set enforces

`FOUNDATION.md` §2.1 line 110:

> if a file cannot be regenerated byte-identically from a fixed OxFunc source state by a program
> with no judgement in it, it does not belong in `data/` — and, added here after A3-S8: if a field is
> a total function of `data/`, it does not belong in `content/`.

The second half is acceptance test (c). Three fields are on its allow-list, each deleted from
`content/` by A3-S8 and computed at build time instead:

| Field | Deleted from | Computed from |
|---|---|---|
| `chip_suppression` | F4 | F3 `axes[].modal_share ≥ 0.90`, F1 `axis_provenance.<key>.oxfunc_tier ∈ {B, C}`, and the vacuity rule |
| `member_count` | F8 category page | the number of F0 `rows[]` whose `category` equals this page's `category_string` |
| `display_label_differs_from_ingested` | F8 category page | `display_label != category_string`, where `category_string` is a verbatim copy of F1 `category` |

Each is named in its schema's `efhForbiddenProperties` block, so the prohibition is readable at the
point where someone would add it back.

## 2. The key-order contract

`FOUNDATION.md` §2.3 line 156:

> object keys in the order given in the schema table (the order is part of the byte-stability
> contract)

JSON Schema cannot express key order. Every object node in this set therefore carries a
**`propertyOrder`** annotation listing its declared properties in the order a writer must emit them.
The rules:

1. **`propertyOrder` is exactly the declared property set.** Not a subset, not a superset. Acceptance
   test (a) fails a schema whose `properties` and `propertyOrder` disagree, and fails any object node
   with `properties` and no `propertyOrder`. (This check found a real omission in `f0-index` on its
   first run.)
2. **`required` ⊆ `propertyOrder`.** Also checked by (a).
3. **An instance is checked against it.** `efh-validate check` reports a *relative* order violation —
   a key that appears after a key the schema orders later. Optional keys may be absent; present keys
   may not be out of order.
4. **Data-keyed objects** (`tests_per_module`, `axis_provenance`, `vintage`, `subject_role`, …) have
   no `propertyOrder`. §2.3 line 160 governs them: *"every data-keyed object emitted in ordinal key
   order"*.
5. **Arrays are ordinal-sorted** (§2.3 line 159) *unless the schema names a semantic order*. Two do,
   and say so in their `efh.keyOrderContract`: F16 `rows[]` is the fixed 12-row battery order given
   by `rows[].label`'s enum, and F10 `episodes[]` is ascending `number`.

Each schema records **why** its order is what it is, in `efh.propertyOrderBasis`:

- `foundation-table` — the order is the order of the rows in the FOUNDATION (or D1) table. Fourteen
  schemas.
- `observed-in-generated-organ` — FOUNDATION gives no table, so the order is read out of the files
  the generator already emits, and `efh.propertyOrderEvidence` records what was read and when. F0,
  F1, F3.
- `foundation-table-plus-declared-append` — the table gives an order, and FOUNDATION later adds
  fields **without saying where they go**. The added fields are appended and the placement is marked
  as declared-here rather than sourced. F6 (`family`, `role_in_family`), F12 (`suspected_lost`,
  `verified`).
- `spec-gap-minimal` — no field table exists at all. F2i, F5r. See §5.

## 3. Annotation keywords used

JSON Schema 2020-12 permits unknown keywords as annotations. This project declares seven; anything
else is a typo and fails acceptance test (a).

| Keyword | Meaning |
|---|---|
| `propertyOrder` | the byte-stability key order (§2 above) |
| `efh` | family, organ, path glob, writer, specifying section, key-order basis |
| `pendingRequired` | a field FOUNDATION requires that the organ does not carry yet, with the reason. Not in `required`, so today's files still validate |
| `efhForbiddenProperties` | a field that must **not** be declared, with the finding that forbids it |
| `efhForbiddenRead` | a field that exists and that no tool may parse (`counts[].figure`, guard G-9) |
| `efhObservedValuesNotInSpec` | a value the organ emits that the spec table does not name |
| `efhObservationNote` | what was measured, over what, and when |

## 4. Divergences between a spec table and the organ as generated

These are recorded rather than absorbed. A schema that quietly widened to match whatever a generator
emits would stop being a specification.

**4.1 F1 `descriptions.short_source` — a third value.** §2.4 line 177 names two values,
`microsoft-english-verbatim` and `differs-from-english-description`, and states 502 for the first.
Measured over all 541 files on 2026-07-31: `microsoft-english-verbatim` 502,
**`no-short-description` 39**, `differs-from-english-description` 0. The 502 matches; the third value
is not in the spec. The enum is left as FOUNDATION writes it, the observation is recorded in the
schema, and `check-organ` reports 39 findings.

**4.2 F3 — six extra fields, one missing required field.** §2.7 line 336 adopts D1 §2.3 unchanged
apart from `modal_share` and the zero occupancies. The generated file adds `declared_kind`,
`backing_field`, `default_value`, `unset_occupancy`, `extraction` and `oxfunc_tree_clean` (permitted:
the schema is open at that level) and **omits `consumer_sites`**, which D1 §2.3 line 201 marks R. The
generator documents its own omission in `extraction.fields_not_emitted`, arguing that a textual grep
is a different fact from a read-site analysis and *"would be published under a name that overstates
it"*. That argument is sound and the field is left required, so the divergence stays visible rather
than being settled by this tool. `check-organ` reports six findings, one per axis.

**4.3 F1 — "26 fields" vs 21 observed.** §2.4 line 168 says *"The existing 26 fields stay"* and does
not list them. The organ carries 21 base top-level fields; the four new ones from D-3, D-7 and D-8
bring it to 24 (25 with the optional `text_integrity`). The observed order is recorded as the
contract and the count discrepancy is recorded here, not resolved by invention.

**4.4 F5 `counts[]` — 20 fields vs "21 required fields".** §2.5's table (lines 221–244) has 20 rows.
T4 acceptance test (b) at line 1184 says *"all 21 required fields"*. The table is the schema
authority, so 20 are encoded. Nothing in FOUNDATION names a 21st.

**4.5 `schema` and `record_version` are missing from several tables.** §2.3 line 161 says every file
carries `schema` and every authored file also carries `record_version`, but F0, F1, F8, F9 and F7's
tables do not list them, and no F0/F1 file at HEAD carries a `schema` key. They sit in
`pendingRequired` with that reasoning attached, so nothing is invented and nothing is lost.

## 5. Two families FOUNDATION names and never specifies

**F2i `data/presence/index.json`** — declared at §2.2 line 122 and produced by T2 (§6 line 1182).
No field table exists in FOUNDATION, D1, D2 or D3. The only groundable field is `schema`, from §2.3's
blanket rule. The schema therefore requires `schema`, permits everything else, and carries the gap in
`efh.specGap`. The shape the generator currently emits is recorded as an **observation** in
`efh.observedShapeAtHead` and is deliberately not promoted into `required` — a generator's current
output is not a specification.

**F5r `content/evidence/REGISTER.json`** — declared at §2.2 line 132; §2.5 line 191 gives it a
function (*"minted once, never reused; registered in F5r"*) but no field names. `schema` and
`record_version` are grounded in §2.3. The list of ids is grounded in function but **not in
spelling**, so `record_ids` is marked as a declared key name and left out of `required`.

**`vectors/<function_id>/vN/MANIFEST.json`** — listed in the §2.2 tree at line 143, given no table
anywhere, and read by the §3.7 assert at line 731 (`ASSERT depth != D5 or a suite manifest exists on
disk`). Zero suites exist, so nothing is currently mis-validated, but D5 is unreachable by
construction until the family is specified. Steward decision SD-3 turns on the same absence:
*bit-exact* and *bit-for-bit* are forbidden in Handbook-voice prose until `vectors/` publishes.

## 6. Where ATTRIBUTION-CORRECTIONS overrides FOUNDATION

`ATTRIBUTION-CORRECTIONS.md` §7 wins where it contradicts FOUNDATION. One correction reaches the
schema layer directly and is encoded here, in `f5-evidence-record.schema.json` on
`counts[].comparison_predicate` and `subject_role`, and asserted by `efh-validate selftest` test (d):

**R22–R24 / OT-15 is INVERTED.** FOUNDATION §3.4 lines 605–607 says MATCH, XMATCH, DELTA, SWITCH,
COUNTIF and SUMIF all reach S5 through a tolerant 15-significant-digit comparison. The corrections
show that **MATCH, XMATCH and DELTA use raw IEEE `==`** and are the source's deliberately excluded
**exact-match control group** — `delta_fn.rs:26` is `if lhs == rhs`, `xmatch.rs:240` is `a == b`,
`match_fn.rs` shares xmatch's comparator, none of the three imports `excel_numeric_compare`, and
negative-control tests exist by name. They carry `comparison_predicate: exact-typed-bit-match` and
`subject_role: contrast`. Only SWITCH, COUNTIF and SUMIF carry the tolerant value — and its label
must read **quantise-then-compare**, never *tolerant*: the helper truncates each operand
independently to 15 significant digits and compares exactly, so values arbitrarily close but astride
a bucket boundary compare **unequal**.

Two further §7 corrections are value corrections rather than schema changes, and are recorded next
to the fields they change: **R25 / OT-13** (POWER's `held_out` becomes `false` with
`corpus_was_repair_target: true`) and the OT-4, OT-6 and OT-16 retargets, which belong to T5's
overclaim suite.

Steward decisions carried in the schemas: **SD-1** (F0 `counts.total_entries` is `const 541`),
**SD-2** (F16 exists and F1 delta D-1 is taken), **SD-4** (F5 `attribution:
alias-sibling-inherited`), **SD-5** (F5 `corpus_was_repair_target`).

## 7. What the validator does not check

- **It does not fetch or embed the official JSON Schema metaschema.** Acceptance test (a) is a
  dialect, keyword, type, `$ref`, `pattern` and key-order-annotation conformance walk against a
  checked-in 2020-12 keyword list. It is not a proof that an arbitrary 2020-12 implementation would
  accept these files.
- **It does not check values against reality.** Test (b) checks that a field the rubric *reads* is
  *declared* with a compatible type. Whether the number written into that field is the number OxFunc
  measured is a different question, and `handbook_reverified: false` is on every evidence record
  because nobody here has re-run anything (FOUNDATION §7.2).
- **It implements a subset of JSON Schema.** `type`, `enum`, `const`, `properties`, `required`,
  `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`,
  `maximum`, `pattern`, `oneOf`, `anyOf`, `allOf`, `$ref`, `$defs`. Conditional applicators
  (`if`/`then`/`else`, `dependentRequired`, `dependentSchemas`) are recognised by (a) but **not
  evaluated** against instances, which is why every conditional rule in this set — "required iff
  `class == substrate-identification`", "required iff `kind == lossy-text`" — is written in the field
  description and marked `C`, not encoded as an `if`/`then`. Those conditions are enforced by the
  organ's writer, not by this tool.
- **`pattern` uses a tiny in-crate regex engine** (`regex_lite.rs`) supporting anchors, literals,
  classes, alternation groups and quantifiers. An unsupported construct is a **hard error**, never a
  silent skip, so a pattern cannot quietly stop being enforced.
